## Summary

e13 is a solid epic. The thirteen STRIDE rows each have a working code path. The pay-once, once-per-cause, ownership and shipped-id controls are real and sit at the service layer. The wave gate can really fail (five negative tests covering seven failure shapes), the 59.5 % claim recomputes exactly (1,071 / 1,801), and every one of the 11 built templates is played through the real `ScenePlayer` from a loader-validated def in at least one test. No file is over 300 lines, no function is over 20 non-comment lines (max 19), strict typing holds, every new script and test carries `# story:`, no generated file was hand-edited, there is no network or ad code, and no existing test was weakened (the test diff has zero deletions).

There are **no must-fix findings**. The defects are of one kind: the *validation perimeter* and the *proof* behind a few controls are thinner than the threat model says. Three malformed-def shapes pass `SceneDefLoader` and produce a door or a target a child can never use. One P0 control (`SC-e13s04-P0-02`) is true by construction and cannot fail on the bug it names. The orphan control (`SC-e13s08-P0-04`) does not test a long run. The new save fields have no persistence or tamper test. Eight should-fix items bring the score under the 94 line, so the verdict is FAIL on score even with zero must-fix.

### Should-fix

**B1 — A map lock can name something that never opens, and the lock regex accepts a trailing newline** · should-fix
- Where: `game/scripts/core/step_params.gd:9` (`LOCK_PATTERN`), `:98` (use); test `game/tests/unit/test_step_params.gd` (`test_a_lock_must_name_a_care_step_in_capitals`).
- Evidence: `^[A-Z][A-Z_]{0,23}$` is "capitals", not "a care step". `MapDef.is_locked` opens a door only when the lock is in `CareSteps.ORDER` (`FEED BATH DRESS PLAY SLEEP`). A def with `destination_locks = ["ZZZ"]`, `["CELEBRATE"]` or `["FEDD"]` loads, shows a dimmed door, and can never be opened. The refusal then points at `next_care()`, which is a different step, so the wish bubble tells the child to do something that does not unlock this door. I also ran the pattern headless: both `"ZZZ"` and `"FEED\n"` match (`NL_ACCEPTED=true`). CONVENTIONS §4 already records that `^…$` accepts a trailing newline (BUG-008) and requires `\A…\z`. The test name claims "care step"; the assertion only proves that a lowercase value with `;` fails.
- Threat model: DoS row "a step with no exit", "unreachable targets", and the F-3 grammar perimeter.
- Fix: in `_clean_optional`, accept a lock only if `CareSteps.ORDER.has(lock)` (this also removes the regex and the newline hole). Add two cases to `test_step_params.gd`: `"ZZZ"` and `"FEED\n"` return `bad_id`.

**B2 — No upper bound on `item_ids`; tap templates lay targets out at `160 px × index`, so a long list puts targets off screen** · should-fix
- Where: `game/scripts/core/step_params.gd` (`_needs_items`, `_shared` — no size cap); `game/scripts/templates/t21_touch_each.gd:79`, `game/scripts/templates/t51_prize_pick.gd:80` (`Vector2(160.0 * float(index), 0.0)` in the tray).
- Evidence: `TrayZone` is a 620 px box centred at the bottom (`tools/build_scene_player_scene.gd`). At 1920 px wide the tray starts near x = 650, so the ninth button (index 8) begins past x = 1930, outside the canvas. `t21` `toggle` needs every target, so a nine-item `toggle` def can never finish; `t21` `count_n` clamps its goal to the target count, which is also unreachable. `t51` can never offer the ninth prize. Every other count is bounded (`COUNT_MAX`, `LANE_MAX`, `EDGE_MAX`); `item_ids` is the only unbounded list. `test_template_aspects` proves reachability only for the nine shipped defs.
- Threat model: DoS "a step with no exit"; `SC-e13s02-P2-01` ("every tap target ≥ 120 px at both aspects") holds only for shipped data.
- Fix: add `ITEMS_MAX` (8 for `t21`, `t51`, `t32`; the dress strip scrolls, so it may differ) in `StepParams`, reject with `bad_count`, and add one test that a nine-item `t21` def is rejected.

**B3 — `destination_scenes` is not checked against `SceneCatalog` at load, and `SC-e13s03-P0-04` cannot fail for a shipped def** · should-fix
- Where: `game/scripts/core/step_params.gd` `_map` (`:121`–`:135`, no catalogue check); `game/tests/unit/test_t25_map.gd:89` (`test_probe_def_is_the_house_hub`).
- Evidence: the scenario says "a map door leads nowhere" fails the test. The only catalogue check is at tap time (`t25_map.gd` `_resolve`), where an unknown scene is logged as `map.destination_rejected` and the door silently does nothing. `home_map.tres` could name `not_a_room` and `SceneDefLoader.load_by_id("home_map")` would still return a valid def. The test named P0-04 (`test_open_destination_resolves_a_known_scene`) proves only that one door resolves; `test_probe_def_is_the_house_hub` checks array sizes, not scene ids. The threat model says a bad value is "rejected and logged", which happens, but a dead door shown to a four-year-old is the failure the P0 row names.
- Fix: in `_map`, return `"unknown_scene"` when `not SceneCatalog.is_shipped(scene)` for any `destination_scenes` entry (the three shipped ids pass). Add a loop test over every shipped def with a `t25_map` step.

**B4 — The new save fields `picked_prize` and `prize_cycle` have no round-trip, tamper or old-file test; `SC-e13s05-P2-02` has no e13 test** · should-fix
- Where: `game/scripts/resources/save_data.gd:69`–`:70` (read), `:83`–`:84` (clamp); `game/tests/helpers/save_corpus.gd` (not extended); `game/tests/unit/test_progress_manager.gd` (named in `e13s05.md:71`, no e13 case).
- Evidence: adding the fields with defaults and no version bump is correct under the ADR-005 amendment ("Adding a field: add it with a default; no version bump"). The ADR also requires that invalid ids are dropped on load and that old files load unchanged. The code does both (`_clean_id`, `clampi`). No test proves it: the only `picked_prize` assertions are the happy path in `test_t51_prize_pick.gd` and `test_surfaces_player_e2e.gd`. The fuzz corpus (`save_corpus.gd`, `test_save_fuzz.gd`) knows `equipped_outfits` but not the new fields, so a wrong type, a 70-character id or `prize_cycle = -5` is never fed through `from_dictionary`. The control row `SC-e13s05-P2-02` ("keeps its atomic write and its signatures") points at `test_progress_manager.gd` but that file has no e13 assertion, and its ID is nowhere in `game/tests`.
- Fix: add three cases to `test_progress_manager.gd`: (1) save, `reset_in_memory_only`, load, `picked_prize` and `prize_cycle` survive; (2) a dict without the keys loads with `""` and `0`; (3) `{"picked_prize": "../x", "prize_cycle": -5}` and `{"picked_prize": 7}` normalise to `""` and `0`. Add both keys to the fuzz corpus, tag the first case `SC-e13s05-P2-02`.

**B5 — `SC-e13s08-P0-04` (zero orphans across a long spawned run) does not test a long run and cannot fail on the leak it names** · should-fix
- Where: `game/tests/integration/test_t50_lanes_e2e.gd:99` (the only P0-04 assertion), `game/tests/unit/test_spawner.gd` (no orphan assertion).
- Evidence: the test ticks 6 times, leaves, and asserts `player.get_child_count() == before - 2` (pad and field gone). Spawned items live inside `LaneField`, so even if `t50_lanes._sync_items` never freed them, freeing the field would hide the accumulation: the leak the threat model rates **high** ("a spawned object is never despawned and the room accumulates nodes") is invisible to this test. Story step 4 (`e13s08.md:68`) asks for "zero orphans across a long run" under `-gselect=test_spawner`; that file has no orphan or node-count check. The anti-vacuity register in the test plan (§6) wants "spawn without despawn in a fixture, assert the counter reports it"; nothing like it exists. The code is correct (`_sync_items` frees, `Spawner._age` drops rows, and GUT shows no orphan for the e13 files), so this is a proof gap, not a runtime defect.
- Fix: in `test_t50_lanes_e2e.gd`, run 200 ticks and assert `field.get_child_count() <= lifetime + 1` at every tick (live rows plus the basket); add a control that a `Spawner` whose `_age` never drops rows exceeds the bound, so the bound can fail.

**B6 — The "no ad branch / no lives" source scans are narrow, cover two or three templates, and have no failing-fixture control** · should-fix
- Where: `game/tests/unit/test_t32_reward.gd:59`, `test_t51_prize_pick.gd:41`, `test_t50_lanes.gd:30`; story row `e13s05.md:70` ("no template contains an ad branch").

A `show_rewarded()`, `admob` or `watch_ad` in `t45`, `t0_title`, `t25_map` or any template passes. `SC-e13s08-P1-01` looks for `ShootBullet`, `DecreaseLife`, `ShakeScreen`: those are TutoTOONS verbs, not names a GDScript author would pick, so the realistic regression (`lives`, `shake`, `bullet`) passes. **B7 — `t32_reward` encodes a three-stage mode with two booleans** · should-fix
- Where: `game/scripts/templates/t32_reward.gd:8`–`:9` (`_star`, `_continued`); same shape in `t51_prize_pick.gd` (`_picked` + `_continued`).
- Evidence: the screen has three stages (unlit, lit, carried on); `_continued` is only true once `_star` is true. CONVENTIONS §3.2: "NEVER encode multi-step modes with 2+ boolean flags", and AGENTS.md: "MUST model every state machine with `Fsm`; NEVER use boolean flag clusters". Pan and Steer were converted to `Fsm` with `STATE_*` constants in round 1; these two were missed. Low runtime impact, but it is the exact pattern the project forbids and the next template to copy it will inherit it.
- Fix: a three-state `Fsm` (`STATE_UNLIT`, `STATE_LIT`, `STATE_DONE`; edges `UNLIT→LIT→DONE`, `UNLIT→DONE`; declared empty dwell table with a comment, like Pan). `progress()` returns 1.0 in `DONE`.

**B8 — `SC-e13s04-P0-02` ("completes exactly once") is true by construction** · should-fix
- Where: `game/scripts/components/cleaning_rub.gd:57`–`:58` (`completion_count()` returns `1 if _latched else 0`); `game/tests/unit/test_t23_erase.gd:17` and `:20`.
- Evidence: the scenario fails when "erase completes repeatedly or never". `completion_count` is derived from a boolean, so it can only ever be 0 or 1. If `_consider()` lost its `if _latched: return` guard, the completion reaction (`template.clean` via `TemplateKit.play_hit`) would fire on every call and the test would still pass: it can detect "never" but not "repeatedly". `SC-e13s04-P0-03` ("cannot be un-completed by more rubbing") is weak for a related reason: covered cells only ever increase, so progress is monotonic whether or not `_latched` exists; only a hull change after completion would exercise the latch, and no test moves the hull.
- Fix: count real events. Give the test a `ReactionRecorder` (it exists in the helper set) and assert exactly one `pose`/`sfx` batch after two full rub passes; for P0-03, move the stub hull after completion and assert `progress()` stays 1.0.

## What I checked and found sound

- **Pay-once and once-per-cause.** `CareLoopManager.collect_reward` refuses a tap before CELEBRATE and a second tap, and pays only through `_grant_cycle_reward` (guarded by `_rewarded_cycle_id`). Removing that guard makes `test_the_reward_pays_once_and_stays_lit` fail, because the tap would then pay twice. The second visit shows the star lit and pays nothing. The gift goes through `buy_furniture(id, 0)` only for ids in `FurnitureCatalog.FURNITURE_IDS`, and is idempotent. `PrizeLedger.pick` refuses a second pick in one cycle and a fresh pick opens in the next (`test_the_next_cycle_opens_a_fresh_wheel`).
- **Ownership and shipped ids.** `ProgressManager.wear` goes through `OutfitCatalog.is_wearable` (food id, wrong slot and unknown slot each tested with zero writes). `place_furniture` requires ownership at the ledger and older tests (`test_persistence_invariants`, `test_furniture_placement`) cover the unowned case. `SceneNav.open` and `t25_map._resolve` both require `Ids.is_valid` and `SceneCatalog.is_shipped`; `res://…` and `../home` are tested to open nothing; no path is ever concatenated from a def.
- **Atomic writes.** The `ProgressManager` diff is a behaviour-preserving extraction into ledgers (`OutfitLedger`, `FurnitureLedger`, `StarLedger`, `PrizeLedger`) plus `_commit()`; the `.tmp` rename path is untouched; the file is 299 lines.
- **Validation perimeter that does hold.** Per-field `Ids` grammar, duplicate rejection on unique lists, parallel-array pairing (`hit_poses`, `slot_ids`, `category_ids`, map rows), finite and ranged thresholds, world sizes, tolerances, door positions inside the world, `repeat_count`, lane and spawn counts, mode lists per template, empty `item_ids` per template. `ScenePlayer._load_def` validates both the override and the consumed def. `t21 count_n` clamps its goal to the target count so `repeat_count` cannot make a step unfinishable.
- **Wave gate can fail.** Five negative tests in `test_template_registry.gd` cover seven failure shapes (missing row, scope disagreement, row naming a def without its template, blank cell in five columns, duplicate row, short row). The scope total (1,801) and the claim are read from `SCOPE_LATEST.yaml`; the table sums to 1,071; 1,071 / 1,801 = 59.47 → "59.5"; skipped weight 392 + 130 = 522 = 1,593 − 1,071. Each `replace`-based control asserts a failure, so a silent no-op edit would fail the test rather than pass it.
- **Test integrity.** All 11 built templates are driven through the real `ScenePlayer` from a def loaded by `SceneDefLoader` (`test_surfaces_player_e2e`, `test_bathroom_rub_e2e`, `test_map_player_e2e`, `test_t50_lanes_e2e`), at the three shipped canvases (`test_template_aspects`, whose "lost target" case proves the reachability check is not vacuous). The BUG-062 regression is a real catch: the three-step bathroom test needs a real rub on each step. Mouse-echo (`device == -1`) is dropped in `TouchPad` and tested for rub, map and lanes. Second-finger ownership is tested for Pan and Steer.
- **Fsm tables.** `StepRunner` (unchanged, `STATE_*`, declared dwell for LOAD, INTRO, OUTRO), `CareLoopManager` (`STATE_*`, `LEGAL_EDGES`, empty dwell with comment), `PanPrimitive` and `SteerPrimitive` (`STATE_*`, `LEGAL_EDGES`, declared empty `MAX_DWELL_SEC` with a test that pins it).
- **Bars.** Largest file 299 lines, largest function 19 non-comment lines (independent script over all 65 changed `.gd` files), `type_gate` 0 failures, `# story:` on every added script and test, no `.tscn` or builder changed, `.tres` defs are data, `.uid` and `.import` changes are engine output (the `estrela` → `star` import fix), no `HTTPRequest`, `HTTPClient` or `WebSocketPeer` in `game/scripts`, no `Co-authored-by` or AI footer in any commit.
- **Spec consistency.** 44 live scenarios (48 rows less four withdrawn), P0=17, P1=17, P2=10; every story's scenario IDs match its `-tasks.yaml`; all but eight plan IDs appear in a named test file (the eight are the four withdrawn rows, two evidence rows that are documents, `SC-e13s05-P2-02` (B4) and `SC-e13s09-P1-04`, whose test says "P1-03 P1-04"). `TEMPLATE_TABLE.md` has 13 rows, 11 built, and the scope text, epic title and evidence document agree on 59.5 % built and 88.4 % planned.

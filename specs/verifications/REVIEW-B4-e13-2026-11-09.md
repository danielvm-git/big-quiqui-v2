## Summary

The implementation has substantial real-path coverage, closed catalog navigation, deterministic spawning, pay-once services, and useful anti-vacuity injections. It is not assurance-ready. Two malformed def classes can still load and strand a child, the accepted save rollback rule is not implemented, and two named geometry/hit-testing gates cannot fail on important instances of the bugs they claim to detect.

## Findings

### Must-fix

#### B1 — A valid-looking scene def can load and then fail to exit

`SceneDefLoader._def_problem()` validates the scene id, media, and steps, but never validates `SceneDef.next_scene_id` or `intro_voice_key` (`game/scripts/core/scene_def_loader.gd:42-55`; fields at `game/scripts/resources/scene_def.gd:8-12`). On exit, the player enters its exit path and calls `SceneNav.open()` with that unchecked id (`game/scripts/scenes/scene_player.gd:133-142`). `SceneNav` safely returns `false` for an unknown id (`game/scripts/core/scene_nav.gd:7-16`), but the player is already exiting and has no recovery path. A def with `next_scene_id = "not_a_room"` therefore loads and strands the child.

**Fix:** Validate `next_scene_id` through `Ids` and `SceneCatalog` (and validate `intro_voice_key` through `VoiceKeyResolver`) before returning a def. Add a loader test that injects an unknown next scene and proves rejection, plus a player-path test that cannot enter EXIT with an unresolved target.

#### B2 — Step validation admits unplayable cleaning and dressing steps

`StepParams._rub()` requires items only for `t34`; empty `t23_erase` and `t40_draw_fill` steps pass (`game/scripts/core/step_params.gd:69-81`). `StepParams._dress()` checks only array lengths/counts, not that a non-empty slot/item pair is wearable or that a free-place item is shipped furniture (`game/scripts/core/step_params.gd:184-193`). The tests demonstrate the gap: a carrot-in-neck def is mounted and only fails when tapped (`game/tests/unit/test_t45_dress_decorate.gd:73-82`). Such a step can load but never increment `_changes`, so the player cannot advance.

**Fix:** Require at least one layer for both cleaning templates. For dress rows, reject non-empty pairs unless `OutfitCatalog.is_wearable(slot, item)`; reject empty-slot rows unless the item is shipped furniture, and ensure the runtime exposes only owned free-place items (or otherwise guarantees an available change). Add loader-level negative tests, not direct-template tests only.

#### B3 — The 4:3 rub scenario does not compare rub progress

SC-e13s01-P1-02 says the same rubs must count the same at both aspects. Its test creates a different full-canvas rectangular hull for each aspect and only asserts that the center is inside and one outside point is outside (`game/tests/unit/test_rub_primitive.gd:132-147`). It never compares progress values, normalized cell selection, the actual `QuiQuiRig` hull, or a mounted player. A regression where 4:3 maps rubs to different cells still passes.

**Fix:** Mount the real player/rig at each shipped aspect, replay the same normalized rub path, and assert equal progress after every point (and equal completion). Keep an injected asymmetric mapping to prove the control fails.

#### B4 — `HitProbe` does not model Godot draw/hit order when `z_index` differs

The reachability gate recursively reverses sibling order and returns the first rect hit (`game/tests/helpers/hit_probe.gd:11-27`). Godot CanvasItem ordering also honors `z_index`/relative z; an earlier sibling with higher z can cover a later target, but this probe reports the later target. The anti-vacuity checks inject only a later STOP sibling (`game/tests/integration/test_tray_reach_e2e.gd:68-85`; `game/tests/integration/test_template_aspects.gd:39-47`), so they do not expose this mismatch. This is a gate that cannot fail on an important form of the overlap bug it names.

**Fix:** Either dispatch real viewport GUI input or make the oracle sort by effective canvas/z order (including relative z and top-level behavior). Add a higher-`z_index`, earlier-sibling cover injection that must fail.

#### B5 — ADR-005 unknown-field preservation is not implemented

The accepted rule says unknown save fields must be preserved so a downgrade does not destroy newer data (`specs/adr/ADR-005-typed-save-resource.md:20-27`). `SaveData.from_dictionary()` copies only known keys (`game/scripts/resources/save_data.gd:59-71`), and `to_dictionary()` emits only known keys (`game/scripts/resources/save_data.gd:39-52`). The next save therefore deletes every unknown field. This is forward-save data loss.

**Fix:** Retain unknown keys in a typed `Dictionary` sidecar and merge them back during serialization, with known validated fields winning. Add a disk round-trip test containing a nested unknown field and assert byte-shape preservation after a normal mutation/save.

### Should-fix

#### B6 — The title one-target test omits the real player's Home control

`t0_title` deliberately leaves Home interactive (`game/scripts/templates/t0_title.gd:65-76`), and the real player always contains a 148×148 Home button (`game/scenes/scene_player.tscn:84-92`). The named test constructs a host with no Home and therefore proves only that its synthetic decoration is muted (`game/tests/unit/test_t0_title.gd:6-19`). This does not establish the stated “exactly one interactive target” contract on the shipped tree.

**Fix:** Define whether global Home is excluded from the count. Then mount `title_probe` in `ScenePlayer` and assert exactly one template verb plus the explicitly permitted global control set.

#### B7 — The 59.5% gate verifies arithmetic, not the measured source counts

The gate sums scene weights typed into `TEMPLATE_TABLE.md` and compares them to numbers typed in scope (`game/tests/helpers/template_table_gate.gd:102-127`). The evidence document states that the raw usage report was absent and no extraction ran (`specs/product/TEMPLATE_EVIDENCE_T22_T3.md:7-13`). If a table weight and scope claim are edited together, the gate stays green despite diverging from the measured catalogue. The 1,071 / 1,801 arithmetic is correct, but “recomputed from measured data” is not proven.

**Fix:** Commit a minimal immutable source manifest (template id → measured count plus provenance/hash), and derive both table totals and scope comparison from it.

#### B8 — Two changed functions exceed the 20-line bar

Static counting found `SaveCorpus.entries()` at 33 non-comment lines (`game/tests/helpers/save_corpus.gd:17-49`) and `test_t23_erase._mount()` at 23 (`game/tests/unit/test_t23_erase.gd:46-69`). Both files changed in this diff and are covered by the convention.

#### B10 — Named-scenario trace metadata is incomplete

`e13s03-tasks.yaml` omits SC-e13s03-P0-05 from its `scenarios` list even though the story/test plan require it (`specs/epics/e13-wave-1b-primitives-and-templates/e13s03-tasks.yaml:1-7`). Test bodies also do not carry the exact IDs SC-e13s06-P2-01, SC-e13s06-P2-02, or SC-e13s09-P1-04; the last is abbreviated as `P1-04` beside another id (`game/tests/unit/test_template_registry.gd:22-27`). Presence-only story tracing will not catch this drift.

### Consider

#### B11 — Negative source scans are lexical, not semantic

The scan has a useful injected failure, but it only recognizes its fixed verb list (`game/tests/unit/test_template_scan.gd:6-21,30-43`). A renamed loss mechanic such as `health`, `restart_round`, or `knockback` would pass. Treat the scan as a hygiene tripwire, not proof that no fail state exists.

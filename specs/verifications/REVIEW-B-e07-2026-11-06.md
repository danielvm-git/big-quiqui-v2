The gate is honestly green and the epic is mostly well built. It fails on money: **the reward is never
written to disk**, and **the reward screen can be reached with no reward**.

## Findings

### must-fix

1. **`game/scripts/autoloads/progress_manager.gd:168` — the cycle reward is paid in RAM and never saved,
   so it is gone the next time the app opens.** `complete_cycle()` → `_apply()` (`:172-177`) mutates
   `data` and emits `progress_changed`; `save()` is called only by `equip()` (`:145`) and by nothing else
   on the quit path (no `NOTIFICATION_WM_CLOSE_REQUEST` / `_exit_tree` hook exists). e07 is the first epic
   that makes this path reachable, and `specs/epics/e07-sleep-and-celebration-scenes/e07s02.md:19` +
   T-E07-04 (`specs/security/epics/e07/THREAT_MODEL.md`) explicitly claim "one `_apply`, then **one
   save**". Reproduced (probe: complete a cycle, then `data = SaveData.new(); load_or_default()`):
   ```
   after reward: coins=5 writes=0 file_exists=false
   after a simulated restart: coins=0 tickets=0 cycles=0
   ```
   The 393 tests cannot see it because every assertion reads `pm.data`, never the file.
   *Fix:* call `save()` from `_apply()` (or from `complete_cycle()`), and add one test that pays a cycle,
   drops `data`, reloads from `pm.save_path` and asserts `coins == pm.CYCLE_COINS_REWARD`.

2. **`game/scripts/scenes/quarto_sono.gd:97` + `game/scripts/scenes/celebracao.gd:57-74` — the celebration
   can be reached with zero reward, and it then refuses to leave on its own.** `_finish()` requests
   `CELEBRACAO_PATH` unconditionally, while `_credit_sleep()` (`:100-106`) silently declines when the loop
   is not in `SLEEP`; on the other side `_leave()` (`:74`) is only reached when `close_cycle()` succeeded.
   The bedroom door is always tappable — `casa.gd:_refresh_from_care_loop` only sets `modulate`, and
   `tap_button.gd:_activate` checks `enabled`, which nothing sets — so a 4-year-old who taps the dimmed
   bedroom first gets: confetti, the "parabéns" voice, **0 coins / 0 tickets / 0 cycles**, the loop left
   wherever it was, and no automatic return (every other room in the game returns to the hub). Reproduced:
   ```
   coins=0 tickets=0 cycles=0 loop=IDLE stage=Celebracao
   requested=["res://scenes/quarto_sono.tscn", "res://scenes/celebracao.tscn"]   # no casa.tscn
   after Home: requests=["res://scenes/casa.tscn"]                                # only the corner button escapes
   ```
   Every sibling room returns home instead (`cozinha.gd:145`, `banheiro.gd:196`, `jardim.gd:116`,
   `closet.gd:176`), so the bedroom is the only room whose hand-off ignores whether the step was credited.
   It also breaks the intent of e07s02's AC1/AC4: the celebration plays for a cycle that never
   happened, and `CELEBRATE` is never the loop state the scene is closed from.
   *Fix:* in `quarto_sono.gd:_finish()`, request `CELEBRACAO_PATH` only when `credited`, else `CASA_PATH`;
   and in `celebracao.gd:_ready()`, always schedule `_leave()` (e.g. after `close_cycle()`, regardless of
   its return value) so the celebration is never a screen whose only exit is a 120 px corner.

### should-fix

3. **`game/tests/integration/test_quarto_sono_scene.gd:94` — the test named "starts zzz once" does not
   check that.** It asserts `zzz.emitting` after the first tuck, then only `expression_id` after the
   second; a `zzz.restart()` on the second tuck would go unnoticed, which is exactly SC-E07-P0-02's
   subject. The behaviour is correct today (`quarto_sono.gd:77` returns early) — the test just cannot see
   it. *Fix:* `scene.zzz.emitting = false` between the two tucks and assert it is still `false` afterwards
   (verified: this passes against the shipped code and fails against a `zzz.restart()` before the guard).

4. **Two of four stories' frozen contracts were never built, and the audit reports PASS.**
   - `specs/epics/e07-sleep-and-celebration-scenes/e07s01.md:33` freezes `func tuck() -> bool`; no such
     method exists (`quarto_sono.gd` only has the private `_on_snapped` slot handler, `:76`).
   - `specs/epics/e07-sleep-and-celebration-scenes/e07s04.md:30` freezes `game/tests/helpers/cycle_e2e_test_case.gd` / `class_name
     CycleE2eTestCase`; the file does not exist — the harness is inlined in `test_cycle_e2e.gd`.
   - `specs/epics/e07-sleep-and-celebration-scenes/e07s02.md:18` requires the guard "asserted from the scene"; `celebracao.gd` never reads
     `_rewarded_cycle_id`, and `:34` lists a `WishBubble` that `build_celebracao_scene.gd` does not add.
   Specs are the source of truth for the next agent, so a frozen contract that does not exist is a trap.
   *Fix:* implement `tuck()` as the public seam (and drive the test through it), or amend the four spec
   lines to what shipped.

5. **`game/scripts/scenes/quarto_sono.gd:50` and `game/scripts/scenes/celebracao.gd:34` restart the shared
   theme.** Both call `play_music(main_theme.ogg)` unconditionally, but that track is what the hub is
   already playing, and `audio_manager.gd:152` documents the seam: *"`play_music` always restarts, so a
   scene that must not restart a theme asks first"* — `casa.gd:_restore_music` does ask. Reproduced
   (`is_crossfading()` `false` → `true` on celebration mount): the theme restarts from 0 s under the
   congratulation voice, twice per cycle. This contradicts the threat model's own mitigation ("music
   continues rather than restarting").
   *Fix:* guard both with `if not AudioManager.is_music_playing(stream)` as `casa.gd` does.

6. **`game/scripts/scenes/quarto_sono.gd:14` — dead constant, and the bedroom is silent.** `VOICE_PATH`
   is declared and never referenced (and points at `celebration_congrats.ogg`, the celebration clip), so the
   one room that closes the cycle plays neither a voice prompt nor an SFX, while all four sibling rooms do
   (`cozinha.gd:68`, `banheiro.gd:88`, `closet.gd:54`, `jardim.gd:61`). No bedtime line exists
   in `game/assets/audio/voice/pt_BR/`, so this is at minimum an art gap to record; the unused constant and the
   missing lamp/tuck SFX (`tap.ogg`/`drop.ogg`/`success.ogg` are already shipped) are not.
   `AUDIT-e07-epic.md:41` reports "No dead code / duplication PASS" — this line is dead.

7. **`game/tests/integration/test_cycle_e2e.gd:100` — the E2E claims more than it runs.** `_finish_room()`
   has five branches and is called once, with `CareSteps.SLEEP` (`:159`); the FEED/BATH/DRESS/PLAY branches
   (~35 of its 46 lines) are unreachable dead test code. So the file looks like the door-to-door journey its
   story title names ("Casa → Cozinha → … → Celebração → Casa") and is not one. Separately, e07s04 AC4
   (`specs/epics/e07-sleep-and-celebration-scenes/e07s04.md:23`, "each scene passes `GeometryOracle` … during the journey") is not implemented: the four
   `GeometryOracle` hits in the file are the aspect constants, there is no `audit()` call.
   The stated boundary itself (`specs/epics/e07-sleep-and-celebration-scenes/e07s04.md` §1, test header `:5-9`) is defensible — per-room gestures *are*
   proven by `test_feed_e2e` / `test_bath_e2e` / `test_closet_e2e` / garden — but dead branches are worse
   than either honest choice. *Fix:* delete the four unused branches (keeping the boundary note) and either
   call the oracle per stage or drop AC4.

8. **Bookkeeping contradicts itself, and one timestamp does not exist.**
   `specs/execution-status.yaml:56` records `completed_at: "2026-11-06T16:60:00-03:00"` — minute 60 is not
   a valid ISO-8601 instant, so any consumer that parses it (dashboard, Allure report) gets an error or a
   wrong sort order. And `specs/epics/e07-sleep-and-celebration-scenes/epic.yaml:5` still says
   `status: in_progress` while `specs/execution-status.yaml:22` says `e07: done` and all four stories are
   `done`; every archived epic (`e01`–`e06`) carries `status: done`. *Fix:* `17:00:00`, and one status.

9. **`DESIGN.md:21` and the shipped tint disagree.** `DESIGN.md` defines `night_slumber_tint = #2B2D5C`
   as "Canvas modulate tint during `SLEEP` lamp-off state"; `quarto_sono.gd:16` uses
   `Color(0.42, 0.45, 0.72)` (#6B73B8) on the background only. The code's choice is the safer one for a
   pre-reader (T-E07-01) and the design row is the one that is wrong on both value and scope, but as it
   stands the design system document lies about the game.
   *Fix:* rewrite the row to the shipped value and to "background only", or use the token.

### consider

10. `game/scripts/autoloads/scene_manager.gd:108` — the guard runs **before** the request is validated, so
    a request later rejected as `same_scene` (`:110-112`) still closes `CELEBRATE`. Not reachable in the
    shipped flow (the only scene mounted while in `CELEBRATE` neutralises its own Home via
    `_step_requested`), but it is a latent ordering bug: close the cycle on the successful path only.
11. `close_celebrate_if_needed()` is effectively unreachable in real play: `celebracao.gd:_ready()` closes
    the cycle one frame after mount, so the loop is `IDLE` for the whole time the child can tap anything.
    The E2E's "detour mid-cycle" (`test_cycle_e2e.gd:193`) never enters `CELEBRATE` either — only the unit
    test drives the guard. T-E07-05's coverage is thinner than `AUDIT-e07-epic.md` implies.
12. `game/scripts/scenes/celebracao.gd:14-15` — `COINS`/`TICKETS` duplicate
    `ProgressManager.CYCLE_COINS_REWARD` / `CYCLE_TICKETS_REWARD` in a scene that does not pay; only the
    tests read them. Test expectation should be `pm.CYCLE_COINS_REWARD`.
13. `game/scripts/scenes/quarto_sono.gd:64-66` — the guard `if fsm.state != STATE_SLEEPING and not credited`
    never refuses in the credited case, so the lamp still works after `FINISHED`: mid-fade to the
    celebration the child can light the room back up (`toggle=true, lamp_on=true, bg=white, state=FINISHED`).
    Cosmetic, but the condition reads as a double negative and should be `if fsm.state != STATE_SLEEPING`.
14. `test_quarto_sono_scene.gd:69` asserts `background.modulate` and `rig.modulate`, which is a real
    guard on `_apply_lamp` but would not catch a `CanvasModulate`-based tint that dims the whole canvas
    (the failure mode T-E07-01 exists for). A three-line "no `CanvasModulate` in the tree" assertion closes it.
15. e07s02 AC5 ("`HomeButton` leaves early without paying twice") is untested — nothing taps the
    celebration's Home in the suite.
16. `ProgressManager.dress()` has exactly one caller, `closet.gd:_apply_saved_look` (`:123-127`), so the
    bedroom and the celebration show the neutral rig rather than the outfit the child picked. Out of e07's
    written scope, but the celebration is where she looks at herself.

## What looks right

- **One owner for money.** `CareLoopManager._grant_cycle_reward()` (`:152-160`) pays on the *transition*
  into `CELEBRATE`, guarded by `_rewarded_cycle_id`, and the celebration deliberately refuses to pay —
  the double-reward defect the audit describes is genuinely gone. Two cycles pay twice (10/2/2 verified),
  one cycle pays once, and re-mounting the celebration pays nothing.
- **The night tint is on the background.** `_apply_lamp()` touches `background.modulate` only; the
  assertion is meaningful (not satisfied by an artless rig) because the same suite's `GeometryOracle` run
  fails closed on a rig with no painted geometry (`geometry_oracle.gd:_audit_rig`).
- **Particle placement is correct at `_ready`.** Contrary to my initial suspicion, the layout *is* resolved
  when `_ready` reads it: confetti lands at `(960.0, 532.4)` against a painted centre of `(960.0, 530.0)`.
- **The tuck is idempotent in code**, not just in the test (`quarto_sono.gd:77-78`), and the second tuck
  preserves `sono` and does not restart the burst.
- **`SceneManager.request_scene` is now 14 body lines** with `_park` and `_close_celebrate_for_detour`
  extracted; no function in the new production/tool files exceeds 20 non-comment lines, and no new file
  exceeds 300 lines (largest: `test_cycle_e2e.gd` 204).
- **House rules hold:** no `Label` in either new scene; every hit target ≥120×120 and inside the viewport
  (plush 132, lamp 120, home 120); `GeometryOracle` + `STEP_ROOM_SPEC` green on `1920×1080` and
  `2048×1536` for both scenes; all input goes through `TapButton`/`TouchDraggable`, which both filter
  `device == -1`; `# story: e07sNN` on every new script, test and builder.
- **The committed `.tscn` files are what the builders produce** — I regenerated both and diffed: the only
  difference is Godot 4.7's per-save `unique_id`, no geometry drift.
- **`test_casa_scene.gd` replacement is a real upgrade:** the e03-era "doors stay pending" test is gone and
  all five care doors are now asserted to navigate to their own scene.
- **The three "defects the tests caught" are consistent with the tree** (no payment in the celebration, the
  two whitelisted `CELEBRATE` targets in `scene_manager.gd:81-86`, the E2E asserting the end state), though
  as a single-commit history I can only verify the fixes, not the failures.
- **Test/report arithmetic checks out:** 6 + 4 + 2 + 3 = 15 new tests, 378 → 393 exactly.

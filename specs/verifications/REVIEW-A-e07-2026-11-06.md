## Findings

### must-fix

1. `game/scripts/autoloads/progress_manager.gd:168-176` (`complete_cycle` → `_apply`) — **The cycle reward is never written to disk.** `_apply` mutates `data` and emits `progress_changed`, but nothing calls `save()`. The only `save()` call sites in `scripts/` are `equip()` (`:145`) and the function itself, and there is no lifecycle hook (`NOTIFICATION_APPLICATION_PAUSED`/`WM_CLOSE_REQUEST` returns no hits). I confirmed with a probe against the real autoloads: after `FEED→…→SLEEP→CELEBRATE`, `coins == 5` and `ProgressManager.write_count == 0`. Why it matters: e07s02 AC3 and THREAT_MODEL.md:33 both say "one `_apply` … **then one save**" (T-E04-04). On iPad the app is routinely killed from the switcher straight after the party. The child loses the +5 coins, +1 ticket and the `completed_cycles` increment, and the quarto/celebração tests (which read in-memory `pm.data`) cannot see it. The audit lists T-E07-03/04 as "closed", and that is not true. Fix: call `save()` in `_apply` (or in `complete_cycle`, so the `add_coins` HUD mutators do not each write). Add a test that asserts `write_count == 1` after entering CELEBRATE and that a fresh `ProgressManager.load()` sees the coins.

### should-fix

1. `game/scripts/scenes/celebracao.gd:10`/`:57-75` and `quarto_sono.gd:97` — **Out-of-order entry strands the child on the celebration.** The hub lets the child open any door (`casa.gd:103-108` navigates regardless of `next_step`; the dim is cosmetic). If she opens the bedroom from IDLE, `_credit_sleep` is skipped (`quarto_sono.gd:103`) but `_finish` still logs `sleep.finished` and requests the celebration (`:97`). The celebration mounts, `close_cycle()` returns false at `:61-62` before `_leave()`, and no Casa request is ever made. The child sits on confetti with only the HomeButton, no reward and a "finished" diary entry that never happened. The same dead end occurs if `CareLoopManager.reset()` runs between SLEEP's credit and the mount (state IDLE). Fix: make `_finish` request the celebration only when it credited, and when `close_cycle()` finds the loop not in CELEBRATE, call `_leave()` anyway. Add a test for each.
2. `game/scripts/autoloads/scene_manager.gd:20-22,108` — **The detour whitelist includes the hub, which can leave the loop stuck in CELEBRATE.** The reward is already paid on entry, so closing before Casa would be safe. As written, any request for Casa that arrives while the loop is in CELEBRATE (a parked request landing during the SLEEP→celebration fade) leaves the hub with every care door refusing — the exact T-E07-05 brick. Only `CELEBRACAO_PATH` needs the exception. Alternatively, have `CasaScene._ready` call `close_celebrate_if_needed()`. No test covers either whitelisted path (`test_care_loop_manager.gd:244-258` only checks `album.tscn`), so the whitelist's behaviour is untested in both directions. The author's defect #2 was found by luck, not by a test pinning the exception.
3. `game/tests/integration/test_cycle_e2e.gd:190-205` — **The "detour mid-cycle" E2E does not test a detour from CELEBRATE.** The loop is in SLEEP when it requests `closet.tscn`, so `_close_celebrate_for_detour` is a no-op. The only assertions are that Casa mounts and has a door, both true with or without e07s03. It never asserts `clm.state_id()` or the cycle after the detour. The spec calls it an end-to-end proof of T-E07-05, and the AUDIT table repeats the claim. Fix: reach CELEBRATE (do not let the celebration mount, e.g. a no-op loader as the unit test does), detour, then assert IDLE and a usable hub; or rename it honestly.
4. `game/scripts/scenes/quarto_sono.gd:65` — **Wrong lamp guard.** `if fsm.state != STATE_SLEEPING and not credited` is true only when the scene is finished *and* uncredited. After a normal finish (`FINISHED`, `credited == true`) the guard is false and the lamp still toggles back on after the child has been put to bed, while the celebration is in flight; in the uncredited case (item 1) it refuses. The intent reads like `fsm.state != STATE_SLEEPING` alone. Visible symptom: the room lights up again behind the party transition. Fix the condition and add `test_the_lamp_is_inert_after_finishing`.

### consider

1. `game/scripts/autoloads/care_loop_manager.gd:113-117` — `reset()` zeroes `_rewarded_cycle_id` and `cycle_id` while `ProgressManager` keeps its state, and `ProgressManager.complete_cycle` has no guard of its own. The probe shows `reset()` + replay pays 10 coins / 2 cycles. `celebracao.gd:7-8` claims "`ProgressManager` refuses a second payment for the same cycle", which is false; the manager's ledger is the only guard and it is in-memory. Reset is test-only today, so this is not a live defect, but fix the comment, or persist the last rewarded cycle in `SaveData`, since `cycle_id` also restarts at 0 every launch.
2. `game/scripts/scenes/celebracao.gd:37,74` — `close_cycle()` calls `_leave()` from `_ready`, so the party lasts about one fade (`scene_manager` fade 0.4 s). The spec says confetti plus voice, "not on a loop", but a 4-year-old gets under a second of it and the voice line is cut by the transition. If a hold is intended, `_clock_sec` is already ticking and unused — it looks like the hold was dropped. No test pins a minimum dwell. Product call, not a bug.
3. `game/tests/integration/test_quarto_sono_scene.gd:77` — the "never the rig" assertion is real for `rig.modulate` (the rig is a sibling of `Background`, not a child, per `quarto_sono.tscn`), but it would not catch a tint applied to the rig's layers (`self_modulate` or child nodes), and the test never checks that the rig has art. Add `assert_eq(layer.modulate, WHITE)` over the rig's children and an assertion that at least one layer has a texture.
4. `quarto_sono.gd` and `celebracao.gd` both carry identical `_play_stream`, `_care_loop`, `_log` bodies (and `_leave`/`_request` twins). The audit says "no duplication"; the duplicate exists, but is within the house pattern of the earlier rooms. A shared helper is a later refactor.

## What looks right

- **Money, single path.** Entry to CELEBRATE is the only payer (`care_loop_manager.gd:126-129`), guarded per `cycle_id` and tested to pay once across a double mount (`test_celebracao_scene.gd:79-92`). I could not get two payments through the real flow, nor zero (apart from the persistence gap above). Moving the payment out of the scene was the right call.
- **Detour wiring.** Putting the guard at the single door (`SceneManager.request_scene`) rather than in each scene covers every route, and `close_celebrate_if_needed` is idempotent and never pays.
- **Tuck idempotence.** `_on_snapped` returns early once `tucked`, so a second snap neither restarts the particles nor touches the `sono` face. `_finish` goes through `Fsm.transition_from`, so SLEEP is credited once.
- **House rules.** No `Label` text; `GeometryOracle` + `STEP_ROOM_SPEC` on both canvases for both new scenes; hit targets 120×120 (`quarto_sono.tscn`: lamp and home 120×120, plush 132×132); `.tscn` files come from `build_*_scene.gd` builders; new files are 92–203 lines (≤300); every new function is ≤20 lines.
- **E2E honesty (focus 5).** The boundary is stated in the test header (`test_cycle_e2e.gd:3-8`), in the `_walk_steps` doc comment, in the e07s04 spec and in the AUDIT. It is defensible, because the earlier four rooms have their own suites and the cycle is the subject. It does not hide a gap in the room mechanics. The one genuine hole is the "detour" test (should-fix 3), which overstates what it proves.
- **Audit candour.** The three "defects the tests caught" check out against the code and the history (double reward, whitelisted targets, unobservable intermediate state). Declaring the art gap (no `abajur`/`cobertor`) is the honest thing to do.

## Findings
### must-fix
None.

### should-fix
1. `game/scripts/components/quiqui_rig.gd:359-379` (+ `:344-352`) — the fit is re-derived from the **current expression's** opaque rect on every `_apply_expression`, so each pose is stretched to the same box height. Measured with a throwaway probe (deleted, tree clean): `base`, `pulando`, `carente`, `sono`, `acenando`, `molhada`, `brilhando`, `prazer`, `careta`, `mastigando` all report `painted_h = 0.574`, top y = 316. But the shipped opaque heights differ (base 868 px, `sono` 777 px, `carente` 821 px, `pulando` 843 px with feet at row 917, not 943). Consequences: (a) `sono` is magnified ≈ 12 % relative to `base`, `carente` ≈ 6 %, so the character visibly pops in size on every expression swap in the care loop; (b) `pulando` can never leave the ground, because the opaque bottom is re-pinned to the pivot; (c) `_fit_box_to_art` changes the box *width* per expression, so the tap surface and mouth-zone proximity change with the pose. No record states this — `DESIGN.md` §3, `ADR-008` and `BUG-013` all describe "the painted character equals the box" as if it were a property of the art, but it is a property of re-normalising every pose. This is the same class of defect this cycle exists to remove (an unstated behaviour). Fix: either fit once from the rest pose (`NEUTRAL_EXPRESSION`) and keep the scale constant across expressions, or add one sentence to `ADR-008` and `BUG-013` saying each pose is normalised to the box height and that the size pop is accepted. No test pins either behaviour today.

2. `wish_bubble` group literal at `game/scenes/casa.tscn:194` and `game/tools/build_casa_scene.gd:140` — deferral accepted as cosmetic; the casa test would fail if the two drifted.
3. Outfit/headwear/glasses layers reuse the expression's scale and offset (`:375-379`). It holds for the four shipped outfits (probe: painted height 0.574, feet 0.780 each; `vestido_florido` is 13 px wider than base, so painted *width* is not equal to the box), but a future hat taller than the head would make painted height exceed the box and the oracle would then fail correctly. The docs say "equals" for height only; keep it that way.

## What looks right

- Opaque measurement: all 18 shipped `quiqui_*.png` are 1024², with hard-edged alpha (bbox at alpha > 0 equals bbox at alpha ≥ 128), so `Image.get_used_rect` is not inflated by soft shadows. Import is `compress/mode=0` (lossless); no VRAM compression is configured in `project.godot` or the export presets, so `get_image()` stays readable in the iOS export.

- Bubble clearance: because every pose is fitted to the same top edge (y = 316 on 2048×1536), the head-top does not move with the expression, so `carente` cannot reach the bubble.
- No network, telemetry or PII regression in the two changed files (docs only). Strict typing holds in the code I read. Round 5 touches no product code or tests.
- Fowler smells: none new. The existing "Speculative Generality" risk is the `_fit_box_to_art` guard for non-0.5 anchors, which no builder uses.

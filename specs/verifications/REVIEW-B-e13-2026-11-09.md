## Findings

1. **B1 — must-fix — `game/scripts/scenes/scene_player.gd:207`**
   - **Evidence:** The player only invokes a template's `advance()` and `progress()`. Seven catalogued templates (`t23_erase`, `t40_draw_fill`, `t25_map`, `t45_dress_decorate`, `t32_reward`, `t50_lanes`, and `t51_prize_pick`) create no input controls and connect no host input in `setup()`. Their behavior is reachable only through test-only direct calls such as `note_rub()`, `activate()`, `snap()`, `collect()`, `tick()`, and `pick()`. In particular, `t50_lanes` has no `advance()`, so the player never ticks its spawner. Their probe defs can load but cannot be played by a child, contrary to the vertical targets and acceptance criteria.
   - **Suggested fix:** Have every template mount visible 120 px input surfaces in `setup()`, connect them to its behavior, advance time-driven behavior through `advance(delta)`, and remove/disconnect everything in `teardown()`. Add ScenePlayer integration tests that complete each probe through synthesized touch rather than direct method calls.

2. **B2 — must-fix — `game/scripts/templates/t0_title.gd:47`**
   - **Evidence:** `_add_verb()` creates a plain `Button` but assigns no size, anchors, icon, or text. Its default rect is zero-sized, so the title's only verb is invisible and untappable. The template also has no `teardown()`, leaving the stale button on the shared player host after completion. The unit test bypasses both defects by calling `press()` directly.
   - **Suggested fix:** Mount a visible `TapButton` (or visual-backed equivalent) with at least `120×120` size and a declared icon, then queue it for deletion and disconnect it during teardown. Exercise it with `TouchSim` in the player.

3. **B3 — must-fix — `game/scripts/templates/t32_reward.gd:11`**
   - **Evidence:** Entering `CELEBRATE` already calls `_grant_cycle_reward()` in `care_loop_manager.gd:142-146`. Consequently, `setup()` sees `_already_paid() == true`, `progress()` immediately returns `1.0`, and ScenePlayer exits the reward step before a tap. Also, `gift_id()` only returns the first def id; no code grants or persists that free gift. This does not implement “collect with a tap” or the free T39 gift.
   - **Suggested fix:** Separate “earned” from “collected” in the cycle ledger. Let `collect()` atomically claim the pending cycle reward and gift once, persist both through their owning services, then light the star. Re-entry should read the claimed state without paying again.

4. **B4 — must-fix — `game/data/scenes/home_map.tres:8`**
   - **Evidence:** The map probe declares destination ids/scenes/locks but no `destination_positions`; `StepDef` has no destination-icon field at all. `t25_map.activate()` is also callable independently of `PanPrimitive.end_allows_tap()`, so the required drag-cancels-tap rule is not enforced by the template. The fixture-only unit step supplies positions and tests pan and activation separately, masking the broken shipped probe.
   - **Suggested fix:** Add and validate icon and position arrays, populate them in `home_map.tres`, mount destination `TapButton`s at those positions, and gate activation through the same touch ownership/tolerance flow that ends the pan.

5. **B5 — must-fix — `game/tests/unit/test_template_registry.gd:23`**
   - **Evidence:** The completeness gate counts rows marked `built` and checks only that three files exist. It does not prove that a built id is registered in `TemplateCatalog`, that the named scene actually consumes that template, or that the named test exercises it. Coverage is hard-coded as `1071.0 / 1801.0`; `TEMPLATE_TABLE.md` contains no per-template scene counts from which 1,071 could be derived. The gate therefore cannot detect several failures it claims to gate.
   - **Suggested fix:** Add measured scene counts to the table, sum built rows, compare that sum and percentage to scope, assert `TemplateCatalog.is_known(id)`, load each named def and find a matching step, and verify a traceable scenario/test record. Include negative fixtures for each missing link.

6. **B6 — must-fix — `game/scripts/components/steer_primitive.gd:11`**
   - **Evidence:** New stateful components use ad-hoc flags instead of the mandatory `Fsm`: Steer uses `_dragging`, Pan uses `_active`, and CleaningRub combines `_holding` with `_latched`. No new component or template instantiates `Fsm`. Besides violating the explicit-state-machine convention, Pan and Steer carry no touch index, so their APIs cannot enforce the required single-finger owner under multi-touch.
   - **Suggested fix:** Model gesture ownership and lifecycle with declared `Fsm` edges/dwell tables, track the owning touch index, reject non-owner move/release events, and test interleaved two-finger streams plus cancellation.

7. **B7 — should-fix — `game/scripts/core/scene_def_loader.gd:30`**
   - **Evidence:** Validation stops after checking the template id. None of the new per-template fields are validated: modes, thresholds, finite world sizes, lane/spawn bounds, id grammar, or equal-length destination/item/slot arrays. Malformed data can therefore boot and silently become zero-position doors, open locks, missing slots, or invalid diary ids. This weakens the threat model's stated grammar perimeter.
   - **Suggested fix:** Add closed, template-specific parameter validation before mounting. Reject malformed ids, non-finite or non-positive geometry/cadence values, unsupported modes, duplicate ids, and mismatched parallel arrays with `scene.def_rejected`.

8. **B8 — should-fix — `game/scripts/components/scrub_gesture.gd:16`**
   - **Evidence:** `begin()` starts the loop SFX immediately on press. `CleaningRub.begin_gesture()` and `t34_rub_reveal.begin_gesture()` call it before any point has passed the hull check, so pressing the tool and moving only over the background still plays rubbing audio. This contradicts the acceptance rule that the first valid rub starts audio and an outside rub does nothing.
   - **Suggested fix:** Arm the gesture on press but start the loop lazily when the first `consume(point)` succeeds; keep `stop()` idempotent for release, cancellation, teardown, and freed targets.

9. **B9 — should-fix — `game/tests/integration/test_t50_lanes_e2e.gd:6`**
   - **Evidence:** The “E2E” test directly instantiates the template, calls `tick()` forty times, and asserts that a host to which the template never adds children has zero children. That orphan assertion cannot fail. The bathroom “E2E” similarly calls `note_rub()` directly and never mounts ScenePlayer or sends touch. These tests are fast but not behaviorally capable of detecting B1, B2, or actual signal/input teardown failures.
   - **Suggested fix:** Mount `scene_player.tscn` with each probe def, drive controls via `TouchSim`, advance the player, assert runner completion, then exit and inspect real spawned/control nodes and signal cleanup.

10. **B10 — should-fix — `game/scripts/templates/t45_dress_decorate.gd:26`**
    - **Evidence:** `snap()` verifies id grammar and membership in the def's item/slot arrays, then calls `ProgressManager.equip()` without checking ownership. A crafted or mistaken def can equip any syntactically valid id. The e13 threat model explicitly requires ownership verification before a save call, but the test covers only an invalid uppercase id.
    - **Suggested fix:** Resolve items through an owned-item/catalog service before `equip()`, reject valid-but-unowned ids without writing, and add that threat-model case to the test.

11. **B11 — should-fix — `specs/epics/e13-wave-1b-primitives-and-templates/epic.yaml:3`**
    - **Evidence:** The epic title still claims `88.4%`, and both `epic.yaml:5` and `specs/execution-status.yaml:55` leave e13 as `planned`, while all stories are marked done and scope/table state 1,071 of 1,801 (59.5%). The e13s06 acceptance criterion required every 88.4% claim to be rewritten.
    - **Suggested fix:** Change the epic title to the measured 59.5% claim and reconcile epic lifecycle status with the completed stories and verify record.

12. **B12 — consider — `game/scripts/components/rub_primitive.gd:74`**
    - **Evidence:** Coverage is a fixed `4×4` bounding-box grid. The denominator counts cells whose centers lie in the polygon, while the numerator accepts any in-polygon point mapped to a cell. On concave or narrow hulls, a cell can count in the numerator but not the denominator, allowing early completion; 16 cells are also a coarse proxy for covered area.
    - **Suggested fix:** Use one consistent cell-in-hull rule for numerator and denominator and choose resolution from hull size/brush radius. Add concave and narrow-hull tests before treating the value as an area ratio.

## Findings

### must-fix

**1. `game/tests/helpers/geometry_oracle.gd:167-177`, `game/scripts/components/quiqui_rig.gd:275-285`
— the "rig height 55–65 %" assertion measures an empty `Control` box, not QuiQui; the character is
still ~42 % of the height on the primary device.**

`_audit_rig_height` computes `rect.size.y / canvas.size.y` from the `QuiQuiRig` node's global rect.
Since this cycle the box is anchored `0.2059 … 0.78` and therefore grows with the canvas, but the
art inside it does not: `_update_layout` computes `factor = minf(box.x / art.x, box.y / art.y)` and
`box.x` is a fixed 640 px (casa) / 700 px (titulo), so the scale is **width**-limited on every
taller canvas. The art is a 1024×1024 texture; measured:

| Canvas | rig box (what the oracle reads) | art actually drawn | feet |
|---|---|---|---|
| 1920×1080 | 640×620 → **0.574** | 620 px → 0.574 | 0.780 |
| 1920×1440 (4:3 expand) | 640×826.7 → **0.574** | 642 px → **0.446** | 0.780 |
| 2048×1536 (iPad 4:3) | 640×881.8 → **0.574** | 642 px → **0.418** | 0.780 |

Titulo is the same: 0.574 box vs 0.575 / 0.487 / 0.457 art.

Why it matters: `DESIGN.md:31-32` says "QuiQui occupies 55 %–65 % of viewport height". F2's
complaint was "rig height / canvas 0.43 vs design 0.55–0.65" — the number F2 raised is **0.43, and
it is now 0.446**. The box moved and the character did not. `test_a_correctly_anchored_rig_passes_the_care_room_spec`
(`test_geometry_oracle.gd:120-137`) passes the spec with a rig node that contains **no art at all**,
which demonstrates the vacuity directly. ADR-008's own words apply to itself: "A product requirement
is only 'verified' if the assertion can fail for it" — this one cannot fail for the requirement it
claims.

Secondary effect of the same cause: the box is now 185 px (4:3 expand) / 240 px (2048×1536) taller
than the art, i.e. 22–27 % of the rig box is empty.

Suggested fix (both halves are small, and the observable already exists):
- drive the art scale from height — `factor = box.y / art.y` — and widen the box to match, e.g. in
  `_notification(NOTIFICATION_RESIZED)` set `offset_left/right = ±(size.y * RIG_ASPECT / 2)`; the art
  then stays 620 px at 16:9 and reaches ~826 px at 1920×1440 without colliding with the door columns
  (measured clear width at that canvas: art would span x ≈ 547…1373, doors end at 232 / start at 1688);
- assert on `QuiQuiRig.get_visual_global_rect()` (already implemented, `quiqui_rig.gd:199`) instead
  of the node rect, in `_audit_rig_height`/`_audit_rig_feet`, and add the 2048×1536 art-ratio case to
  `test_casa_scene.gd` next to the existing `has_area()` assertion (`test_casa_scene.gd:69`).

**2. `specs/verifications/FIX-e01-e02-2026-11-04.md:24-26`, `specs/adr/ADR-008-…md:51`,
`specs/bugs/BUG-002-expand-anchoring.md:15-18,42`, `specs/verifications/AUDIT-e01-e02-2026-11-04.md:310`
— the closure evidence for BUG-002 compares art-before with box-after and reports it as one series.**

The table reads "Rig height ratio: 0.430 → **0.574**" (1920×1440) and "0.400 → **0.574**" (2048×1536).
The *before* values are the rig's **art** ratio at `cc6a139` (the box was 640×620 and equalled the
art); the *after* values are the **box** ratio. Like-for-like, the after values are 0.446 and 0.418.
BUG-002 is marked `status: fixed` with "Expected: … QuiQui keeps 55–65 % of height", ADR-008's
Consequences say "rig 0.574 of the height" and "a taller box grows the art" (`BUG-002:42`), and the
AUDIT disposition table repeats "4:3 rig 0.574". None of those statements is true of the character.

Why it matters: this is precisely the failure mode the cycle was chartered to remove — "a green gate
standing in for an unproven requirement" (`FIX:76`). A reviewer, or e03, reading these records would
believe the HIGH layout finding is closed and copy the same pattern into nine more rooms.

Suggested fix: either land finding 1 and re-measure, or restate the requirement. If the intent is
really "~600–700 px tall" in absolute pixels (DESIGN §3's parenthetical), then the ratio guard is the
wrong contract and `CARE_ROOM_SPEC.rig_height_min/max` must become px bounds — but the record must
then say that the 4:3 canvas keeps a 620 px character on purpose, and F2's "55–65 % of viewport
height" line in `DESIGN.md:31-32` must be corrected, because the two readings cannot both hold.

### should-fix

**3. `game/scripts/components/quiqui_rig.gd:66` — the rig's tap surface is now larger than QuiQui;
blank background above her head counts as affection.**

The `QuiQuiRig` box is `MOUSE_FILTER_STOP` and its `_gui_input` accepts any press in the box. On
16:9 box height == art height (620 == 620), so this was previously exact; on 4:3 the box carries
185–240 px of empty space above the character, and `CasaScene._on_rig_tapped` (`casa.gd:110-115`)
answers with `rig.set_expression("rindo")` plus a squash. A 4-year-old tapping the wall above
QuiQui's head gets a reaction, and the gesture is not attached to anything they can see, which
`DESIGN.md:33-34` (hit targets) and the "no hidden state" rule both push against.

Suggested fix: reject taps outside `get_visual_global_rect()` in `_gui_input` (one `has_point` test,
`get_visible_rect()` semantics), or shrink the box to the art once finding 1 is fixed.

**4. `game/tests/helpers/geometry_oracle.gd:30` and `:220` — dead code added by a cycle that
removed dead code.**

`EDGE_INSET_TOLERANCE: float = 24.0` is declared and never read (inset limits come from the spec
dictionary instead); `get_tree_nodes_in_group` is now a one-line alias for `_collect` and has no
caller (`_audit_hit_targets` was switched to `_collect`). Both contradict the Boy Scout rule in
`AUDIT-e01-e02:…` (F13: "no dead code").

Suggested fix: delete both.

**5. `DESIGN.md:29` — the normative composition rule contradicts the shipped builders.**

It now reads: "anchors **and offsets** are expressed as ratios of the canvas (never absolute
`1920×1080` pixels)". The packed scenes are the opposite: anchors are ratios
(`anchor_top = 0.205926`, `anchor_bottom = 0.78`) and every offset is absolute pixels
(`offset_left = 64.0`, `offset_right = 232`, `-812.0`, `-320/320`), which is the right design —
insets and hit-target sizes should not scale with the canvas.

Why it matters: this line is the rule e03–e10 will copy, and it is already false for both shipped
scenes; it also invites a future "fix" that turns the 36 px inset into a ratio, which would break
`DESIGN.md:33-34`'s minimum hit-target rule on small canvases.

Suggested fix: "anchors are ratios of the canvas; offsets are absolute pixels (insets, fixed
hit-target sizes, and the rig's feet-line offset); the rig box **height** is a ratio."

## What looks right

Things I tried to break and could not:

- **BUG-001 is genuinely fixed, and provably so.** Root and background measure exactly 1920×1080 /
  1920×1440 / 2048×1536 across all three canvases, and `set_anchors_and_offsets_preset` with no
  `size` assignment is the correct Godot idiom. The oracle's new *upper* bound
  (`geometry_oracle.gd:90-97`) plus `test_an_oversized_background_is_caught` closes the `>=`
  asymmetry that let it ship green. Re-running both builders reproduces the checked-in geometry
  exactly (only per-run `unique_id`s differ — see consider 13-adjacent note: the builders are not
  byte-idempotent, but they are geometrically idempotent).
- **Feet line, dots, HUD, doors** land where the design says on every canvas: feet 0.780 / 0.926,
  dots 36 px from the bottom, HUD 36 px from the top-right, doors 168² on the edges at ratio rows,
  all ≥120×120 and inside the canvas. The 16:9 frame is pixel-identical to `cc6a139` (sub-pixel
  differences only: bubble 30.0 → 30.4).
- **`SquashSpring` is a faithful extraction.** I diffed the new `advance()` against the removed
  `tap_button.gd` loop: identical semantics, including the frame-drop `while` and the
  `_elapsed + remaining < limit` boundary. `TapButton`'s four existing transform assertions still
  pass, so "zero behaviour change" holds for this seam.
- **`LogSink` is the right seam, not a Middle Man.** Two static entry points for the two real cases
  (`Node` in the tree, `RefCounted` Fsm), both silent no-ops when `Log` is absent; ten copies
  collapsed to one, and the `frame: null` degradation the audit praised is preserved.
- **BUG-003/F4 payloads are truthful and now asserted through `Log.last_line`** — `care.abandon`
  captures `fsm.state` *before* the transition (`care_loop_manager.gd:74-80`), and
  `test_dwell_timeout_logs_milliseconds_truthfully` asserts `limit_ms == 2000` **and** that
  `limit_sec` is gone, which is the assertion that matters.
- **BUG-009**: `_successor(IDLE)` returns `""`, `complete_step("IDLE")` is refused, and only the five
  care doors dim — `CasaScene._refresh_from_care_loop` iterates `CareSteps.ORDER`, so VILA is never
  touched. The regression test covers both the initial frame and a post-transition frame.
- **BUG-012's path validation is real.** `ART_PATH_PATTERN` rejects `../`, uppercase and any scheme;
  I could not construct a path that escapes `res://assets/art/`. Same for `Ids.PATTERN` on save/art
  ids, and the diary's looser pattern is documented as the auditor's, not merged into it.
- **Privacy holds.** No `HTTPRequest`/`HTTPClient`/`WebSocketPeer`/`OS.shell` anywhere in
  `game/scripts`, `game/tests`, `game/tools`; the only `user://` writes are the diary and the save
  file; `Log.last_line` mirrors exactly the redacted line that goes to disk, so it adds no exposure.
  Refusing prose under `msg` (BUG-004) is a defensible *stricter-than-auditor* policy for a
  children's diary, and it is now pinned by `test_prose_under_msg_is_refused_by_policy` instead of
  being invisible.
- **Test quality elsewhere is honest.** The 27 new tests all execute (143 − 116 = 27, exactly the
  number added) — none are silently skipped. `test_hiding_mid_pulse_returns_the_visual_to_rest`
  asserts the transform, not the getter, which is the assertion F6 asked for;
  `test_a_resize_moves_the_feet_to_the_new_bottom_edge` exercises the real
  `NOTIFICATION_RESIZED` path; `test_the_reward_degrades_when_progress_manager_is_unreachable` proves
  the ledger advances without a sink (it would fail if `_grant_cycle_reward` were skipped).
- **`CareSteps` as the single vocabulary owner** is the right de-duplication: `CareLoopManager`
  derives its `STATE_*` and `STEP_ORDER`, `CasaScene` derives `DOOR_SCENES`/`WISH_ICONS` keys, and
  `test_the_cycle_vocabulary_has_a_single_owner` pins the identity rather than a copy.
- **The records were corrected, not just added.** ADR-002's `SafeStage` MUST is marked superseded,
  ADR-008 names what it supersedes, and `DESIGN.md` §3 now offers one option instead of two — the
  contradiction the audit flagged as F2's discovery clause is genuinely gone (finding 5 is about the
  wording of the surviving rule, not about the contradiction).
